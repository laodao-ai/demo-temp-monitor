# 超温告警推送尽力而为：只发一次，不重试，不落库，允许丢失

**Status: Proposed** · 来源 change：`alarm-notify`（2026-10-16）

超温告警要推送到外部接收端，由接收端去找值班的人。推送会遇到接收端慢、挂掉、返回错误的情况，需要定一个送达保证。

本项目是教学示例。每条超温读数都推送一次（ALM-04 不去重），由接收端按 `device_id` 合并。每条告警都已经写进 WARN 日志。

## Decision

- 每次推送只发一次。超时、连接失败、非 2xx 都直接丢弃，记一条 ERROR `alarm push failed`，不重试（ALM-07）。
- 待发推送放在内存里的有界队列（100 条）。队列满时丢弃新推送，记 ERROR `alarm push dropped`（ALM-08）。
- 不落库，也没有发件箱。进程退出时，在 5 秒预算内能发多少发多少，剩下的丢弃，并记 WARN 和丢弃条数（RUN-06）。
- WARN 日志 `over-temperature alarm` 是告警的完整记录，推送只是告警的一个副本。

## Considered Options

- **内存重试（比如 3 次加退避）**：否决。重启时照样会丢；接收端挂掉时，重试会让队列更快塞满。持续超温时，后续读数本身就会再推一次，等于已经有了重试。
- **先落库，再由后台投递（至少送达一次）**：否决。需要新表、新的存储接口方法，内存实现和 PostgreSQL 实现都要改。对教学示例来说太重，而且收益只覆盖"只超温一次就恢复"这种情况。
- **只发一次，失败就丢弃，记录下来（采用）**：实现最小，服务除了一个内存队列外没有新状态。

## Consequences

- 系统：推送路径只有一个内存队列和一个 worker，不改数据模型。
- 用户：短暂超温一次的那条推送可能丢失，值班的人收不到。每次丢失都有 ERROR 或 WARN 可查，告警本身在 WARN 日志里。
- 已知边界：接收端长时间不可用时，期间的推送全部丢失，不会补发。
- 反悔成本：改成"保证送达"需要发件箱表、投递状态和两个存储实现的改动，相当于一次新的改动。
