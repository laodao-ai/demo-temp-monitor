# 告警通知按跨线触发，告警状态只放内存，发送失败不重试

**Status: Accepted** · 来源 change：`alarm-notify`（2026-10-17）

超温时要通知值班人员。服务把告警通知 POST 给接收方，由接收方决定通知谁。告警日志仍然是每条超温读数写一条。需要决定的是：哪些读数触发告警通知、触发依据的状态存在哪里、发送失败了怎么办。术语见 `GLOSSARY.md`。

## Decision

- **跨线触发**：每台设备有一个告警状态，取值为「正常」或「告警中」。
  - 「正常」时收到一条超温读数，状态变为「告警中」，发一条 `alarm`。
  - 「告警中」时收到一条不超温的读数，状态变回「正常」，发一条 `recovered`。
  - 同一个告警期内只发这两条。
  - 不做滞回：温度在阈值附近反复跳动，就按规则成串地发。
- **告警状态只放进程内存**：注册、注销、服务重启都会把设备复位为「正常」，复位不发告警通知。不建表。
- **发送失败不重试**：超时、连接失败、非 2xx，只写一条 ERROR。告警状态照常切换，不回退。

## Considered Options

- **每条超温读数都发一条告警通知**：否决。设备持续超温时，每次上报都会打扰值班人员。只有接收方自己能去重时才可行，而群机器人做不到。
- **冷却时间（每台设备每 N 分钟最多发一条）**：否决。需要多一个配置项，值班人员也很难预料下一条什么时候来。
- **把告警状态写进数据库**：否决。要加表、加迁移，还要处理注销时的级联。教学示例为了"重启后不丢状态"付出这些成本，不划算。
- **发送失败时把状态退回「正常」，靠下一条超温读数再试一次**：否决。要把发送结果回传给 service。另外，失败结果传回之前，`recovered` 可能已经入队，这种竞态要额外处理，成本高于收益。
- **跨线触发 + 状态只放内存 + 不重试（采用）**。

## Consequences

- **用户视角**：
  - 一个告警期内，值班人员只会收到一条 `alarm`，回落时再收到一条 `recovered`。
  - 有三种情况会让通知不完整：
    - 一条 `alarm` 没送达，整个告警期内不会再通知，最后只收到一条孤立的 `recovered`。
    - 服务重启：可能多收一条 `alarm`，或者收不到 `recovered`。
    - 设备在告警中被注销：收不到 `recovered`。
- **系统视角**：`service` 不再是"构造后没有可变状态"，它多了一张由一把锁保护的告警状态表。只有配置了 webhook 才会建这张表。发送者是单个 goroutine 加一个有上限的队列，与 HTTP 共用 5 秒的退出时限。
- **开发视角**：告警状态的规则可以用假的 Notifier 做单元测试；发送部分可以用 `httptest` 测。都不需要数据库，也不需要外网。
- **以后要改**：如果要保证可靠投递，有两种做法：在接收方前面放一个带重试的中转，或者把告警状态落库并加上重试。后一种需要新写一篇 ADR 来取代本篇。
- **主次**：优先保证不打扰值班人员、实现简单；投递可靠性放在次要位置。
